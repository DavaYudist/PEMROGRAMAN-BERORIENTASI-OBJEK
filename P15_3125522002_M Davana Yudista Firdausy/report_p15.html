A. DASAR TEORI SINGKAT

Modul 15 merupakan puncak evaluasi dari rangkaian praktikum Pemrograman Berorientasi Objek berbasis Project-Based Learning (PBL). Tujuan utama modul ini adalah menguji penguasaan individu dalam mempertanggungjawabkan rancangan arsitektur, membuktikan stabilitas aplikasi melalui demonstrasi fungsional langsung, serta menunjukkan kelincahan kognitif dalam menelusuri source code dan mengimplementasikan perubahan kecil secara terarah:

  • Pertanggungjawaban Keputusan Desain (Architectural Accountability): Setiap struktur data, kelas enkapsulasi, hierarki relasi, dan blok penanganan eksepsi harus dapat dijustifikasi secara ilmiah mengapa pola tersebut dipilih dan bagaimana pola tersebut melindungi konsistensi data.
  • Ketahanan Siklus Transaksi (State Resilience): Demonstrasi menuntut pembuktian empiris bahwa operasi yang gagal atau ditolak (misalnya input kode duplikat atau format korup) tidak merusak atau memodifikasi status data yang telah ada sebelumnya di memori utama.
  • Penelusuran Kode Antar-Kelas (Cross-Class Code Tracing): Mahasiswa dituntut memahami alur interaksi objek melintasi batas kelas: dari penerimaan input di kelas Main, validasi invarian pada Buku, penegakan keunikan di Perpustakaan, hingga serialisasi berkas I/O.
  • Adaptabilitas Perubahan Terarah (Targeted Code Evolution): Kemampuan menganalisis dampak dari penambahan fitur baru (misal fitur pencarian parsial berdasarkan substring judul) serta meletakkannya pada kelas yang tepat dengan mematuhi prinsip Single Responsibility.

F. EVALUASI DAN JAWABAN PERTANYAAN MODUL 15

1. Keputusan desain apa yang paling membantu menjaga konsistensi data?
Jawaban: Keputusan desain yang paling krusial adalah penerapan Pola Pemuatan Penyangga Defensif (Staging Buffer Loading Pattern) pada kelas Perpustakaan dan Validasi Invarian Fail-Fast pada konstruktor Buku. Dengan membaca berkas ke dalam instans koleksi sementara terlebih dahulu, aplikasi tidak pernah mengosongkan memori aktif sebelum seluruh baris berkas terbukti valid 100%. Ditambah dengan enkapsulasi unmodifiableList, pihak luar tidak memiliki celah untuk merusak struktur data internal koleksi.
2. Bagian mana yang paling sulit diubah, dan apa penyebabnya?
Jawaban: Bagian yang paling sulit diubah adalah mekanisme parsing dan format serialisasi file teks. Hal ini dikarenakan format berkas terikat langsung dengan struktur baris (delimiter pipe |) dan ketergantungan urutan indeks token kolom. Apabila di masa mendatang entitas Buku ditambahkan atribut baru (seperti pengarang, tahun terbit, dan stok), maka kode pembacaan (split) dan penulisan berkas di seluruh sistem harus dimodifikasi secara serentak, serta berkas lama yang sudah ada di disk memerlukan skrip migrasi agar tidak memicu error format kolom.
3. Pengujian apa yang paling kuat membuktikan aplikasi bekerja sesuai kebutuhan?
Jawaban: Pengujian Siklus Lengkap Persistensi dan Konsistensi Pasca-Kegagalan (Round-Trip Persistence & Negative Fault Injection). Pengujian ini tidak hanya memverifikasi bahwa data yang disimpan dapat dimuat kembali 100% identik tanpa kehilangan karakter, melainkan juga menyuntikkan data rusak (baris cacat atau kode ganda) untuk membuktikan bahwa ketika kegagalan terjadi, memori aktif lama tetap aman terlindungi tanpa ada data yang musnah.
4. Jika fitur baru ditambahkan, class mana yang perlu berubah dan mengapa?
Jawaban: Pembagian perubahan mengikuti prinsip keterpisahan tanggung jawab: jika fitur tersebut berhubungan dengan logika pencarian, filter, atau agregasi data (seperti fitur cariBukuSebagianJudul), maka perubahan ditempatkan pada kelas domain Perpustakaan agar logika dapat digunakan kembali. Kelas Main hanya mengalami penambahan opsi menu perutean untuk memanggil metode tersebut dan menyajikan hasilnya ke layar pengguna. Namun jika fitur menambah atribut entitas, maka kelas Buku dan metode I/O pada Perpustakaan wajib diperbarui.

G. REFLEKSI INDIVIDU MAHASISWA

Kontribusi Nyata yang Dapat Dibuktikan: Mengembangkan arsitektur terintegrasi yang memadukan OOP fundamental, Java Collections, penanganan eksepsi defensif, persistensi berkas berbasis Java NIO, serta suite pengujian otomatis regresi bebas kegagalan (100% PASS) dari Modul 11 hingga Modul 15.
Keputusan Desain yang Paling Dipahami: Prinsip Information Hiding dan Defensive Programming. Memahami secara mendalam mengapa referensi internal koleksi tidak boleh diekspos secara mutable, mengapa validasi keunikan wajib dijalankan sebelum mutasi state, serta bagaimana koleksi penyangga sementara mencegah terjadinya silent data corruption.
Kelemahan Teknis yang Perlu Ditingkatkan: Saat ini penyimpanan berkas teks lokal masih bersifat sekuensial dan belum mendukung transaksi konkuren multi-thread. Rencana pengembangan lanjutan adalah menerapkan read-write locking dan mengintegrasikan layer Object-Relational Mapping (ORM) atau konektor database JDBC.
