A. DASAR TEORI SINGKAT

Koleksi objek yang disimpan dalam struktur data berbasis memori utama (RAM) bersifat volatile, yang berarti seluruh siklus hidup objek akan tereliminasi secara permanen begitu proses aplikasi dihentikan atau komputer dimatikan. Agar informasi bisnis dapat bertahan melintasi sesi eksekusi, aplikasi membutuhkan mekanisme persistensi data ke media penyimpanan sekunder (Non-Volatile Storage) menggunakan berkas teks terstruktur.

Aspek-aspek arsitektural penting dalam persistensi file teks pada Java meliputi:

  • Format Serialisasi Berbasis Delimiter: Mengonversi state objek menjadi representasi baris teks berpemisah (misal karakter pipe |) dengan format kode|judul. Penggunaan delimiter menuntut validasi ketat agar karakter pemisah tersebut tidak terkandung di dalam nilai data itu sendiri guna mencegah ambiguitas pemecahan token (token parsing error).
  • API Modern Java NIO (java.nio.file): Menyederhanakan penanganan berkas melalui method deklaratif berperforma tinggi seperti Files.write(Path, Iterable, Charset) untuk menulis sekumpulan baris secara langsung dan Files.readAllLines(Path, Charset) untuk membaca seluruh berkas ke dalam List<String> dengan pengkodean standar StandardCharsets.UTF_8.
  • Pola Pemuatan Atomik Defensif (Atomic Defensive Loading): Kesalahan umum dalam pemuatan file adalah langsung membersihkan koleksi aktif (daftarBuku.clear()) sebelum validasi isi berkas tuntas. Jika berkas di tengah jalan memiliki baris rusak atau kode duplikat, koleksi aktif akan hilang tak berbekas. Praktik terbaik menuntut pembentukan objek ke dalam koleksi sementara (staging buffer). Setelah seluruh baris terbukti valid 100%, barulah koleksi aktif ditimpa secara atomik.
  • Penanganan Eksepsi I/O: Operasi disk bersifat tidak pasti (dapat terjadi disk full, access denied, atau file not found). Seluruh interaksi fisik wajib mendeklarasikan atau menangani java.io.IOException secara proporsional.

E. EVALUASI DAN JAWABAN PERTANYAAN MODUL 12

1. Apa perbedaan antara data di memori (RAM) dan data di berkas (Storage)?
Jawaban: Data di memori (RAM) bersifat volatil dan tersimpan dalam bentuk referensi instans objek Java aktif yang mendukung manipulasi berkecepatan sangat tinggi, namun seluruh datanya akan musnah seketika saat aplikasi ditutup atau komputer dimatikan. Sebaliknya, data di berkas (Storage) disimpan secara permanen (non-volatil) pada media penyimpanan fisik dalam format stream biner atau teks terstruktur, sehingga datanya tetap lestari dan dapat direkonstruksi kembali pada sesi eksekusi berikutnya.
2. Mengapa data dari berkas tetap harus divalidasi saat dimuat kembali ke aplikasi?
Jawaban: Berkas teks di penyimpanan sekunder berada di luar domain kontrol runtime JVM dan rentan terhadap modifikasi eksternal, korupsi transmisi, atau manipulasi manual oleh pengguna (misal membuka file dengan teks editor lalu memasukkan kode ganda atau menghapus delimiter). Jika data berkas dipercaya secara buta (blind trust), aturan invarian objek (seperti kode unik dan non-null) akan dilanggar dan berpotensi memicu kegagalan sistemik di kemudian hari.
3. Mengapa tidak boleh langsung mengosongkan koleksi sebelum memastikan berkas valid, dan bagaimana teknik koleksi sementara mencegah hilangnya data?
Jawaban: Jika method clear() dipanggil di awal proses pembacaan file, lalu pada baris ke-5 terjadi kegagalan format atau duplikasi, maka pembacaan akan dihentikan oleh exception dan aplikasi berakhir dengan kondisi koleksi aktif telah kosong melompong (kehilangan data sebelumnya). Dengan teknik koleksi sementara (staging collection), seluruh parsing dan validasi dilakukan pada objek terisolasi terlebih dahulu. Pengosongan dan penggantian koleksi aktif hanya dieksekusi pada langkah pamungkas setelah 100% data terbukti valid secara atomik (All-or-Nothing).
4. Mengapa method simpan() harus dipanggil ulang setelah terjadi penambahan atau penghapusan objek di memori?
Jawaban: Mutasi state seperti tambahBuku() atau hapusBuku() hanya memodifikasi struktur data ArrayList di memori utama (RAM) secara lokal dan tidak memiliki sinkronisasi otomatis ke storage disk. Tanpa memanggil eksplisit method simpan(), modifikasi data tersebut tidak akan pernah dituliskan ke dalam berkas fisik sehingga jika aplikasi ditutup secara normal maupun mengalami crash, seluruh perubahan yang baru saja dilakukan akan hilang permanen.
